> **定位**：说明本仓库**如何系统性地做测试**，补充 [`AI_PROJECT_CONTEXT.md`](AI_PROJECT_CONTEXT.md) 中的行为事实；技术细节仍以全景文与代码为准。  
> **面试「问题→解决」叙事**（先讲风险再讲手段）见全景 **§1.0**。

## ① 测试分层（一定会被问）

我把测试拆成多层，从**单元**到**系统**再到**质量门禁**，保证不同阶段的质量覆盖。

| 层级 | 在本仓库中的落点 | 典型手段 | 解决的问题 |
|------|------------------|----------|------------|
| **单元测试** | `tests/`，`conftest.py` + **FakeRedis** | pytest、内存假 Redis、不启容器 | 算法与语义（幂等、限流、熔断键语义等）**快速回归** |
| **接口 / 契约测试** | `test_api_contract.py`、`test_fault_injection.py` 等 | Flask `test_client`（或 httpx 对外）、JSON 形状与状态码 | **HTTP 契约**是否稳定、错误体是否可预期 |
| **系统测试** | `docker compose` + **`/fault/*`** + `fault_demo.py`、（可选）`k8s/` | 真实 Redis、多 worker、混沌注入、端到端脚本 | **多组件协作**、故障注入下的行为是否可接受 |
| **性能测试** | `benchmark_compare.py`、可选 `locustfile.py` | 并发 HTTP、**治理实例 vs 基线**、多轮中位数 | **容量与尾延迟**、回归是否在门禁阈值内 |
| **质量门禁** | `quality_gate.py`、`security_scan.py` | 读 **JSON 报告**、阈值判定、CI 阻断 | **发布前**把「变坏」挡在流水线里 |

**面试一句话**：分层是为了在成本可控的前提下，把**证明正确**（单测）、**证明没撕协议**（契约）、**证明在真环境 + 故障下仍可用**（系统 + 注入）、**证明没变慢/没更抖**（压测）串成一条链，最后用 **gate** 固化标准。

## ② 覆盖模型（重点）

面试官想听的是：**你怎么系统性地测**，而不是「想到哪写到哪」。

本项目的用例设计按下面几个维度收口（与 `tests/`、`security_scan`、故障注入相互配合）：

| 维度 | 含义 | 在本仓库中的例子 |
|------|------|------------------|
| **正常路径** | 主成功场景 | 建单 201、查单 200、取消 200、幂等回放 200 |
| **异常路径** | 明确失败、可预期错误体 | 400 参数错、404 无单、409 幂等冲突、429 限流、503 库存忙 |
| **边界条件** | 阈值附近与空/极值 | 超时 202 与 `BUSINESS_TIMEOUT_MS`、限流窗口边缘、`rate_limit` 阈值 |
| **并发冲突** | 竞态与并发 | 同 `X-Idempotency-Key` 并发、多 worker 下订单仍全局一致 |
| **依赖失败** | 下游/基础设施异常 | Redis `ping` 失败、`FakeRedis`/`broken` 模拟连接错误、fail-open 与降级路径 |

**面试一句话**：先用**矩阵**想「正常 / 异常 / 边界 / 并发 / 依赖失败」有没有洞，再落到用例名和报告上；这样答的是**方法**，不是单点 case。

## ③ Failure Model（非常加分）

我把系统里**可能出现的失败**抽象成有限的 **failure model**，再用 **HTTP 故障注入** 有选择地覆盖，而不是靠「手工点一点」碰运气。

| 模型 | 语义（面试怎么说） | 在本仓库中的对应 |
|------|------------------|------------------|
| **latency** | 处理变慢、队列/stack 积压 | `fault:type=latency`，`latency_ms` |
| **exception** | 未预期异常、需走错误处理与指标 | `fault:type=exception`，`error_type` |
| **drop** | 丢请求 / 拒绝服务 / 超时表现为失败 | `fault:type=drop`，`drop_rate` |
| **slow_db** | 资源竞争、慢 IO、带随机抖动的慢路径 | `fault:type=slow_db`，`base_ms` / `jitter_ms` / `timeout_rate` |

**面试一句话**：我把失败**分模**，用注入在**可控**前提下复现，再结合熔断（对外常表现为 202）、限流（429）等治理手段，观察 **error / degraded / 延迟分位** 是否仍在门禁内。

更细的 API 与 Redis 键语义见 [`AI_PROJECT_CONTEXT.md`](AI_PROJECT_CONTEXT.md) §4～§5。

## ④ 覆盖率思路（方法论，非炫耀数字）

不设具体「百分之几」也能讲清楚：**测的不是行号，而是风险面**。

| 思路 | 关注什么 | 本项目怎么体现 |
|------|----------|----------------|
| **接口覆盖率** | 每个对外路径至少有一条「成功 + 一类典型失败」 | `/order`、查单、取消、探活、`/fault/*`、`/metrics` 等 |
| **状态路径覆盖** | 同一接口在不同前置状态下的分支 | 幂等 `processing` / `succeeded`、熔断开/半开、超时预判 |
| **异常覆盖** | 错误码与 body 契约、依赖失败 | 429/503/202、Redis 异常分支、`security_scan` 分级 |

**面试一句话**：覆盖率对我来说是 **接口 × 状态 × 异常** 的 checklist，再结合 failure model 做注入；数字可以后补，**框架先要站得住**。
