# 性能与行为解读（面试口径）

> **定位**：在已有 **`benchmark_compare`** 与 JSON 报告的前提下，把**系统行为讲清楚**。本节是**定性结论 + trade-off 话术**，不是线上 A/B 的统计结论；与 [`AI_PROJECT_CONTEXT.md`](AI_PROJECT_CONTEXT.md) §2.1 B、§10 门禁字段一致。  
> **门禁里的「相对基线回归」与历史 trend 是否进 gate**：见全景 **§1.0**（诚实边界）。

---

## ① 熔断的影响（典型观察）

**开启熔断**（治理侧相对基线）时，在压测报告里常能看到方向性模式：

- **`error_rate` ↓**（硬失败减少，部分流量被挡在「快速失败」路径外）  
- **`degraded_rate` ↑**（更多请求走 **202** 等**受控降级**，而不是拖死或直接 5xx）  
- **`p95` 往往 ↑ 或更「钝」**（部分样本被快速拒绝/排队语义替代长拖尾，但整体分布会随参数与样本量变化，面试重点是**能解释机制**）

**面试一句话**：熔断本质是用**可控失败**（对外可观测的降级）换**系统稳定性**——不让错误在链条里级联放大；是否在你们场景「划算」由 gate 里的 **error / degraded / p99** 联合约束。

---

## ② 滑动窗口 vs 固定桶

| 算法 | 行为直觉 | 面试怎么说 |
|------|----------|------------|
| **sliding**（滑动窗口） | 时间上**连续**地数窗内请求 | **更平滑**，短期突发对通过率的影响相对温和，**抖动**常更小 |
| **fixed**（固定桶/按秒桶） | 按固定时间片**重置**计数 | 在桶边界容易出现**突刺**（瞬时通过率波动更明显） |

具体默认值见 `RATE_LIMIT_ALGORITHM` 与 compose；对比实验可在同环境下切换算法再跑 `benchmark_compare`。

**面试一句话**：限流不是「挡流量」这么简单，**窗的形状**决定了用户体验是平滑还是被锯齿状切割。

---

## ③ Timeout / 超时保护的 tradeoff

**超时保护**（进锁前用 **`BUSINESS_TIMEOUT_MS`** 与已消耗时间做预算）带来的典型权衡：

- **降低尾延迟风险**：避免请求在已明显来不及的情况下仍挤进临界区，拖占连接与线程  
- **提前返回 202**：用**明确降级**取代长时间悬挂；对调用方来说要看是否接受「可重试/可查询」语义而非强同步成功

**面试一句话**：timeout 是在 **SLA 截止时间**上做决策——用**早失败**换**尾部分位**和**资源可预测性**；与熔断 202 并存时，要能说清**分别是哪一层**在保护系统。

## 与门禁的关系

`quality_gate.py` 读 `reports/benchmark_latest.json`，对 **baseline / protected** 的 **error、p99、protected p95 相对 baseline 的倍数、unstable（degraded+error）** 等做判定；**trend** 文件用于人读波动，不替代主门禁输入。详见全景 **§10～§11**。
