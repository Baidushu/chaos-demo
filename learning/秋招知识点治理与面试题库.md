## 2. 模块知识点 × 深挖底线

> 每个模块分两部分：**事实清单**（必须精确到数字和键名）与**深挖底线**（答不上就危险的问题——这些是面试官判断「项目是不是你的」的探针）。

### 2.1 韧性四件套（被测系统核心）

**事实清单**：

- 限流：IP 维度（`X-Forwarded-For` / `remote_addr`）。默认滑动窗口 = Redis **ZSET + Lua 脚本**（`ZREMRANGEBYSCORE` 清窗 → `ZCARD` 计数 → `ZADD` 记本次 → `EXPIRE`，一条脚本保证原子性；成员名 = 时间戳+uuid 防碰撞）。固定窗口 = `INCR` + 2s TTL。超限 **429**。
- 熔断：CLOSED / OPEN / HALF_OPEN 三态。状态在 **Redis 共享**（多 gunicorn worker 一致）：`cb:open_until`（开闸截止）、`cb:failures`（ZSET，分数=失败时间戳，`BREAKER_WINDOW_SEC` 滑动窗）、`cb:probe`（半开探测占坑，`SET NX` + `CIRCUIT_PROBE_TTL_SEC` 默认 30s）。打开期间请求 **202** 快速失败。
- 幂等：`X-Idempotency-Key`。`SET NX + TTL` 占位 `processing`（`IDEM_PENDING_TTL_SEC` 默认 15s 防死占）→ 成功后写 `succeeded + order_id`。语义：重复请求 **200 回放**、处理中短暂等待后 **202**、同 key 不同 payload **409**。
- 超时预算：进锁前判断 `elapsed + 计划处理时间 > BUSINESS_TIMEOUT_MS` → **202 timeout protected**，不进锁
-
- 。关键：**排队/限流/幂等消耗的时间计入同一个端到端 deadline**。
- 重试：指数退避 + jitter；无 Redis 时重试耗尽后约 68 秒**干净失败** 503，而不是挂死。

**深挖底线**：

1. Lua 脚本解决什么问题？——「清窗+计数+写入」三步必须原子，否则并发下窗口内计数不准（读到旧值再写入）。不用 Lua：WATCH/MULTI 乐观锁重试或客户端拼接都有竞态或多次 RTT。
2. 半开探测为什么用 `SET NX`？——多 worker 同时进入半开，只允许**一个**探测请求打到恢复中的下游，其余直接 202。防「半开瞬间全部流量涌入」把刚恢复的服务再打死。
3. 失败计数为什么用 ZSET 不用 INCR？——滑动窗口需要「过期的失败自动出窗」，ZSET 按分数（时间）裁剪天然支持；INCR 还得单独维护过期逻辑。
4. 限流/熔断在 Redis 挂时 fail-open，业务读挂时 503——为什么策略不同？——治理组件自己不能成为致命单点（Redis 挂了全站 429/熔断更糟）；业务数据是必需依赖，失败必须显式暴露。这是「依赖分级」的判断。
5. 幂等占位 TTL 15s，处理超过 15s 会怎样？——占位过期，第二个同 key 请求可能进来造成重复写。这是「防死占」与「窗口竞态」的权衡，处理时长应远小于占位 TTL，诚实承认这是已知边界。

### 2.2 故障注入与混沌

**事实清单**：4 类故障 `latency / exception / drop / slow_db`，通过 `POST /fault/inject` 在线注册，状态存 Redis `fault:{type}` + TTL **到期自动恢复**；生效点在 `before_request` 业务入口（`drop`→503、`exception`→500、`latency/slow_db`→sleep）；`/fault/*` 自身不套娃（否则无法自恢复）；`ENABLE_FAULT_INJECTION` 与韧性开关正交。

**深挖底线**：

1. 这是**应用内协作式**注入，不等价于网络层 `tc` 丢包/延迟或杀 Pod——测的层次不同（应用逻辑 vs 网络韧性 vs 进存活性），如实区分是加分项。
2. 为什么 TTL 自动恢复很重要？——注入忘了清除导致环境永久污染是混沌工程经典事故，TTL 是「故障必然自愈」的保险丝。
3. 故障状态为什么放 Redis？——多 worker 共享，注入一次全实例生效。
4. **注入接口为什么没有鉴权？被攻击怎么办？**（威胁建模送分题）——项目定位是演示裸接口；`ENABLE_FAULT_INJECTION` 开关可整体关闭（有单测锁行为），`/fault/*` 自身不套娃（保证可自恢复）。生产化四步：管理平面分离（独立端口/服务）→ mTLS+token+RBAC → 全量审计 → 爆炸半径控制（按实例比例灰度注入）。行业对标：Chaos Mesh / Gremlin / AWS FIS 的 agent+平台模式。姿态：**主动承认边界 + 给出生产方案**，见 §8.5。

### 2.3 测试体系（测开主战场，投入最多）

**事实清单**：64 文件 / 667 用例（Redis 可用时 2 个「真 Redis」集成用例自动执行，共 667 passed；无 Redis 时这 2 个自动 skip）。pytest.ini 9 个 marker：unit / smoke / contract / integration / e2e / chaos / slow / redis / resilience，`--strict-markers`。smoke 5 条 3 秒，全量约 5 秒（本机）。FakeRedis = 手写内存版（dict+锁、Lua 语义模拟、zadd/zremrangebyscore 支撑熔断键），FailingRedis 注入 `ConnectionError` 走 fail-open 分支。51 条路由契约测试。api-automation-demo 是独立第二棵 pytest 树（httpx + YAML 数据驱动 + Allure + MockTransport）。

**深挖底线**：

1. 为什么测试不用真 Redis？——确定性（无外部状态泄漏）、快、CI 无 Docker 依赖。三层收益一次讲完。
2. FakeRedis 的局限？——只模拟了用到的语义子集，语义等价靠对照测试保证，它测不出真 Redis 的网络/持久化/主从行为——所以留了 2 个真 Redis 集成用例（标记 `redis`，无 Redis 自动 skip）。**能讲清「测试工具本身的局限」是高级信号。**
3. 测试怎么分层的、为什么分层？——金字塔逻辑：单测（FakeRedis，快、定位准）→ 契约（锁接口形状，防重构回归）→ 集成 → E2E → 部署验证（Docker 配置测试）。反馈速度与置信度的交换。
4. flaky 怎么治理的？——环境隔离（conftest 隔离 `.env` 防真实 key 污染、`monkeypatch` 重置环境变量、basetemp 绕 Windows Temp 权限）、放宽 Docker-Windows 网络延迟下的业务预算。核心态度：**flaky 不是「重跑就好」，是缺陷**。

### 2.4 压测与质量门禁



**事实清单**：A/B 对照 = **同镜像、不同配置**（`ENABLE_RESILIENCE` true/false），5000 治理版 vs 5001 基线版，单一变量。`urllib` 短连接 + ThreadPoolExecutor；`--runs` 多轮取**中位数**；`--warmup` 预热 + `--seed` + session_id 防幂等键串单；P50/P95/P99 用 `statistics.quantiles(n=100)` 近似。门禁阈值：error_rate≤0.05、p99≤450ms、**protected 相对 baseline 的 p95 回归倍数≤1.10**、unstable（degraded+error）≤0.35；benchmark_history 保留 20 份、trend 窗口 10 份比中位数。链路：`quality_gate.py`（压测+安全）→ `unified_quality_gate.py`（+agent_eval、可选 trend P95 比值≤1.15）→ `unified_summary.py`（Gate 失败仍生成）。失败抛 `QualityGateError` / `AgentGateError`，exit 1 阻塞 PR。

**深挖底线**：

1. 门禁的本质是什么？——**发布决策**，不是「全绿心安」。阈值是「可解释的工程判断」：error_rate 5% 是演示量级的容忍线，p95 回归倍数防「性能悄悄变差」。
2. 单次压测方差大怎么办？——多轮中位数 + 历史趋势窗口 + 方差诚实呈现。**不要说「我的数字很稳定」**。
3. 为什么压测客户端可能先成为瓶颈？——urllib 短连接无 keep-alive，线程数受 GIL 约束（IO 密集尚可），单机压单机。真实压测用 wrk / locust（项目里有 locustfile）。
4. 阈值会不会为了「过关」调松？——原则是**可配置但不为过关放宽**；war story：token 重试税阈值 0.60 导致周期性误杀，校正到 1.50 是「修 bug」不是「放水」，同时加了小样本跳过和门禁逻辑单测。

### 2.5 AI 评估（护城河，讲透这个岗位就稳了）

**事实清单**：三类评估器——ScoreEvaluator（启发式：tool_selection_accuracy、arg_accuracy、retry_rate、hallucination_rate、planner_invalid_rate）、JudgeEvaluator（LLM-as-Judge，二元 PASS/FAIL + 结构化推理）、RegressionEvaluator（基线 vs 候选，逐指标 delta + 容忍度）。QualityGate 6 阈值：tool_selection≥0.70、arg_accuracy≥0.70、avg_tool_calls≤10、retry≤0.30、hallucination≤0.10、planner_invalid≤0.10。数据集 56 条、4 类场景（normal/ask_user/workflow/attack）。路由是**确定性护栏 + LLM 双层**：攻击输入和「查询/取消意图但无订单号」直接走规则（安全路径不交给概率性组件），其余给 LLM planner，`validate_plan` 闸门兜底。Prompt 回归 = 基线快照 → 候选同流水线 → 逐指标 delta → 门禁。`eval_variance.py` 多 seed 看方差。LLMGateway 4 Provider（Mock 确定性 / Ollama×2 / OpenAICompatible）。降级链：LLM 不可用 → 规则分析，报告标注 `analysis_backend` 实际来源。

**深挖底线**：

1. 幻觉率怎么定义的？——工具调用场景：调用了不存在的工具/编造了数据集里不存在的订单号等「事实性错误」占总任务比例。**指标可操作化是关键，不是背名词。**
2. 为什么不能只用 pass/fail 断言测 LLM？——输出非确定、语义开放；需要启发式（结构）+ Judge（语义）+ 回归（漂移）三层。
3. LLM-as-Judge 有什么坑？——judge 自身非确定（多轮投票/temperature=0 缓解）、偏置（偏爱长回答/位置偏置）、成本（采样率控制）。诚实说项目用二元判定 + 结构化推理降低主观空间。
4. 为什么安全路径不交给 LLM 路由？——安全决策要**确定性**，LLM 有被绕过概率；规则兜底 + LLM 只做非安全路由，是「护栏模型」思想。
5. Prompt 改了一个词，怎么知道没把系统改坏？——Prompt 回归：同一数据集、同流水线、基线快照对比，退化超容忍度（如 tool_selection 掉超 0.05）阻塞。类比性能回归测试，但作用于质量指标。

### 2.6 安全防护

**事实清单**：4 层洋葱：InputValidator（长度/关键词/正则）→ PromptGuard（**22 种注入模式**：指令覆盖、角色扮演、DAN 越狱、系统提示词提取，可单独启停）→ PermissionChecker（Tool 级访问控制）→ OutputChecker（敏感泄漏扫描）。SecurityPolicy 可序列化（to_dict/from_dict）按环境配置；违规带规则名/严重级别/命中模式的结构化数据进 Trace 审计。演示杀手锏：注入请求 → 403 + 命中模式数。另有 security_scan.py：SQLi 多 payload + 上下文感知分级（5xx 只有体含 DB/SQL 栈才 high，否则 medium——防误报）。

**深挖底线**：

1. 规则匹配防注入的局限？——绕过变体无限（编码、同义改写），生产要加语义分类器/在线学习规则；本项目 22 模式是纵深防御第一层，不是全部。
2. 为什么输出也要检查？——泄露和合规风险在出口；`ignore previous instructions` 拦在入口，但工具返回的敏感数据可能在 answer 里流出去。

### 2.7 可观测性与工程基础

**事实清单**：`/live`（不碰 Redis，秒回，存活探针）/ `/ready`（ping Redis，失败 503，就绪探针摘流量）/ `/healthz`（始终 200，人用诊断；无 Redis 要等 23s 退避——所以不能当探针）。prometheus_client Counter/Histogram 在进程内，`/metrics` 不依赖 Redis。JSON 行日志（event + request_id）。AI Platform 侧 trace_id 贯穿全流水线，类型化事件层次（Agent/Node/Tool/LLM/Evaluation/Gate/Workflow Event）。Grafana 5 个预置大盘。Docker Compose：app + app_baseline + redis + prometheus + grafana（app 带 NET_ADMIN）。gunicorn `--workers 2`。CI 三工作流（ci / ai-quality / qa），qa.yml 主链 12 步。Windows 坑：全仓显式 `encoding="utf-8"`、pytest basetemp、GBK 控制台不用 emoji。

**深挖底线**：

1. 为什么多 worker 下状态必须去 Redis？——进程内存不共享，进程内熔断计数 = 每 worker 独立计数，阈值语义被 worker 数稀释。
2. Histogram 怎么出 P99？——服务端累计桶（bucket 计数），Prometheus 用直方图分位数**估算**；项目诊断工具里对直方图做线性插值算 p50/p99。注意：**不是**存每个请求的延迟。
3. `db_lock` 是进程内锁，多 worker 会怎样？——各 worker 并行建单，全局一致性靠 Redis 语义（订单键、幂等键）兜底；诚实边界：单键仍可能成热点。

| 5 | 限流阈值 80→20/s     | 限流阈值高于本机应用容量，压测永远不过载，A/B 过载保护演示失效                 | 认识到阈值必须**低于被压系统容量**才构成有效实验                   | 恢复过载演示能力                        |
| 6 | 超时预算 50→200ms    | Docker-Windows 网络延迟让压测 Success 失真                 | 区分「演示量级参数」与「生产参数」，按环境调                       | 压测数据可信                          |
| 7 | LLM 根因判定         | 自由文本关键词追词，措辞一变就误判                                 | 根因类别键协议：判定用结构化键、叙事用自由文本                      | LLM 路径三例全部正确诊断                  |

**讲法模板**：「现象 → 我怎么定位（假设-验证）→ 修复 → 怎么防再犯（往往是加测试）」。每个故事 60–90 秒。

## 5. 叙事与行为面

- **为什么硕士搞密码来做测开**：中兴实习接触硬件测试，发现「发现风险、固化质量」的乐趣 → 主动构建这个平台把方法论走通。科研带来的系统能力（读论文、量化实验、方差意识）直接迁移到质量工程（eval_variance 就是方差意识）。**不是逃离科研，是能力复用。**
- **AI 参与度怎么答**：诚实 + 展示掌控。「项目开发有 AI 辅助，但每个设计决策的 why、每个阈值的来源、每个 bug 的定位过程我能讲到底层」——然后**主动**引到一个深挖底线题证明。躲闪是最大错误。
- **最大缺陷**：教学量级、无真实流量、压测单机短连接；改进思路：上 Linux 用 locust/wrk 分布式压、接 tc 网络层 chaos、加 MySQL 丰富存储维度。**能说出缺陷+改进=成熟**。
- **反问环节**：问「团队现在 LLM 评估/质量门禁落地到什么程度？新人 first project 一般是什么？」——展示你在思考这个团队的真实问题。

### 8.1 「手写 vs 企业工具」标准答法（三层结构，必背）

面试官问「为什么不用 LangSmith / NeMo Guardrails / PyRIT」：

1. **学习目的**：自己写熔断器才能讲清 HALF_OPEN probe 竞态，用框架只剩调参——像学 OS 写 mini-kernel。
2. **量级考量**：单机教学量级，上平台要引 API 依赖/费用/密钥管理，是刻意的取舍。
3. **边界同构**：Collector 的 Trace/Span/Event 就是 OpenTelemetry 思想，生产可换 OTel exporter；SecurityGuard 四层与 NeMo rails 划分一致——换实现不换结构。  
   **姿态铁律**：说「我手写了 X 因为 Y，行业对应物是 Z，边界一致」；绝不说「我用不上」或「我的比它好」。

**使用纪律（重要）**：

1. §8/§9 都是**被动弹药**：先立住自己的实现和数字，被问「为什么不用 X」或聊到行业实践时再放对标。开场就报工具名 = 邀请追问 = 被穿。
2. 每个对标点要能答「它和我的实现差在哪一层」——报得出名字是入门，答得出差异是懂行。
3. 差距话术的公式：「我做到 A，团队规模的问题是 B，我的方法在 B 上怎么延伸 + 我理解行业怎么做 C」——把差距讲成「知道边界在哪」，不是「没做过」。
